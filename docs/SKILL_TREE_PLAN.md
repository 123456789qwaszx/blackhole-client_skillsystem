## 1. 게임을 이렇게 읽는다

사용자 설명: 뱀파이어 서바이벌과 같은 구조에서 캐릭터와 액티브 스킬을 없애고, 레벨업 카드 3택을 노드 트리로 바꿨다. Skill은 4종이고, 전기·폭발·처치 시 버프·처치 시 공격 주기 감소 버프로 연쇄를 만든다.

| 뱀파이어 서바이벌 | 이 게임 | 지금 레포 |
|---|---|---|
| 캐릭터 | 없음. Player는 Aim Point만 움직인다 | `Player.AimPoint` |
| 무기 (자동 공격) | Passive Skill 4종 | Breaker, 관통 레이저 |
| 액티브 스킬 | 없음 | 없음 |
| 레벨업 카드 3택 | 노드 트리에서 산다 | 단일 선행 노드 목록과 구매 규칙 |
| 패시브 아이템·진화의 시너지 | 천체 특성의 연쇄: 전기, 폭발, 처치 시 버프, 처치 시 공격 주기 감소 | 전기(연쇄 번개)만 |

이 계획은 두 가지 해석을 전제로 한다. 둘 다 사용자 확인이 필요하다(8절 Q2·Q5).

- 전기·폭발·처치 버프·공격 주기 감소는 **천체(Enemy)의 사망 효과**다. 원작의 전기 천체(연쇄 번개), 초신성(폭발로 보임), 달(파괴하면 일정 시간 Breaker 강화), 혜성(커서 공격이 항상 치명타)과 같은 자리다 [원작]. 원작 플레이어도 전기가 플레이어가 아니라 소행성의 특성이라고 적었다 [원작 S7].
- 노드 구매는 지금처럼 **전투 밖**이다. 카드 3택을 대신하지만 전투 중에 고르지 않는다 [현재 구현].

### "스킬 트리"가 아니라 "노드 트리"

원작 트리의 노드는 Skill 강화만이 아니다. 새 천체·효과 해금, 성장 공급 강화, 레이저 강화 묶음이 있다 [원작 R10]. 트리를 Skill의 일부로 보면 노드가 Skill 안으로 들어가고, 두 시스템이 한 덩어리가 된다.

이 문서는 노드 트리를 **여러 시스템에 보정을 나눠 주는 독립 시스템**으로 보고, Skill 시스템을 그 받는 쪽 중 하나로 본다.

## 2. 세 덩어리와 하나의 접점

```text
[편집]    노드 도구 (F03)
            │ 저장
            ▼
[데이터]  트리 파일 ─┬ 규칙 칸: 노드 ID · 가격 · Grant · 연결선 · 시작 노드
                     └ 표시 칸: 좌표 · 구역(색) · 아이콘 · 이름 · 설명

[전투 밖] 노드 트리 (F01)  ◀── NodeId 구매 요청 ───  트리 화면 (F02)
            │               ─── 노드 상태 · 구매 결과 ──▶
            │ 산 노드 ID
            ▼
          Loadout 컴파일 ── Skill 목록 + 대상별 보정 목록
            │
[경계]    전투 조립 ── 각 시스템에 자기 몫만 넘긴다
            │
[전투 안] Skill 시스템  ◀── 버프 (시간 제한 보정) ──  사망 효과 (전기 · 폭발 · 처치 버프)
          실행 수치 = 기본 ⊕ Loadout 보정 ⊕ 활성 버프
```

노드 트리와 Skill 시스템을 잇는 것은 **Loadout 하나**다. 의존 방향은 한쪽뿐이다.

```text
노드 트리    ──(Skill ID, 수치 이름)──▶  Skill 종류가 공개한 수치 목록
Skill 시스템 ──────────── ✕ ──────────▶  노드 트리   (Skill은 노드를 모른다)
```

### 2.1 소유와 모르는 것

| 시스템 | 소유 | 모르는 것 |
|---|---|---|
| Skill | 종류별 정의·기본 수치·**수치 목록**, 실행 상태, 실행 수치 계산, 전투 중 버프 적용 | 노드, 가격, 선행, 좌표, 무엇으로 해금됐는지 |
| 사망 효과 (S06) | 효과 정의와 수치 목록, 대기열, 종료 규칙, 버프 발생 | 노드, 구매 |
| 노드 트리 (F01) | 노드 ID·가격·Grant, 연결선, 구매 가능 판정, 진행 상태(산 노드, Gold), Loadout 컴파일 | Skill이 어떻게 실행되는지, 수치의 의미 |
| 트리 화면 (F02) | 좌표, 구역·색, 아이콘·이름·설명, 상태 표시, 확대·이동 | 구매 조건 계산 (노드 트리에 묻는다) |
| 노드 도구 (F03) | 편집 화면, 즉시 검증, 미리보기, 저장 | 전투 실행 |

### 2.2 분리를 확인하는 기준

1. Skill 종류를 하나 더해도 노드 트리 코드(구매·그래프·Loadout 컴파일)를 고치지 않는다. 새 종류가 수치 목록을 공개하면 도구의 선택 목록에 나타난다.
2. 노드를 더하거나 선을 바꿔도 Skill 코드를 고치지 않는다.
3. 트리 파일 안의 노드 순서를 바꿔도 전투 결과가 같다.
4. 트리 화면은 NodeId, 구매 결과, 노드 상태만으로 동작한다(CA-004 조건을 잇는다).

1·2는 코드 리뷰 기준이다. "코드를 고치지 않는다"는 계약 테스트로 쓸 수 없다. 3·4는 계약으로 쓸 수 있다.

### 2.3 지금 코드의 결합

| 결합 | 자리 | 결과 |
|---|---|---|
| 효과 종류 이름에 Skill 수치 이름이 들어 있다 (`SkillRadiusAdd`, `LaserWidthAdd`) | `UpgradeEffect.cs` | Skill 하나를 더하면 효과 enum, 대상 검사, `UpgradeModifiers` 분기, `Hud.Describe` 분기 네 곳을 고친다 |
| 노드 쪽 코드가 Skill 수치 구조체를 직접 만든다 | `UpgradeModifiers.Apply` | 노드 트리가 `BreakerStats`·`PiercingLaserStats`의 칸을 안다 |
| 효과를 콘텐츠 노드 순서로 쌓는다 | `UpgradeModifiers.For` | 도구가 파일의 노드 순서를 바꾸면 더하기·곱하기가 섞인 수치의 결과가 바뀔 수 있다 |
| 해금 Skill의 실행 순서가 콘텐츠 노드 순서다 | `SessionAssembler.GiveSkills`, CONTENT_DEFINITION 3.3 | 노드 순서가 Step 안의 Skill 실행 순서를 정한다 |
| 선행이 노드마다 하나다 (`Requires`) | `UpgradeNodeDefinition` | 원작 스크린샷의 격자 묶음(순환이 있는 연결)을 표현하지 못한다 (4.1) |
| 노드 설명 문장을 효과 종류 분기로 만든다 | `Hud.Describe` | 화면도 Skill 수치 이름을 안다 |

CA-004는 P1의 첫 방향(수치마다 효과 종류)을 택하며, Skill이 늘어 실제 반복이 생기면 다시 본다고 적었다(CONTENT_DEFINITION 7절). Skill 4종과 버프가 같은 수치를 바꾸게 되면 그 조건이 된다.

## 3. Skill 시스템

### 3.1 Skill 종류가 공개하는 것

지금 새 종류는 하위 정의, 실행 상태, `PassiveSkills.Create` 분기, Loader 종류 이름을 더한다(CA-003). 여기에 **수치 목록** 하나를 더한다 [제안].

| 공개하는 것 | 예 (Breaker) | 쓰는 쪽 |
|---|---|---|
| 정의와 기본 수치 | `BreakerStats`(Radius, Interval, Damage) | 콘텐츠 |
| 수치 목록 | 피해·반경·공격 속도. 각 수치의 제약과 허용 연산 | Loader 검증, Loadout, 버프, 도구의 선택 목록 |
| 실행 상태 | `BreakerSkill` | `World.Step` |
| 표현이 읽는 상태·기록 | `TickCount`, `LastTickHitCount` | 화면·소리 |

- 수치 목록은 Skill 종류의 코드가 가진다. 노드 트리는 이름으로만 가리킨다.
- 보정 대상이 아닌 값은 목록에 넣지 않는다. 예: 레이저의 `BoundaryRadius`는 공간 값이다.
- 모든 Skill의 공통 수치는 두지 않는다. 같은 "피해"라도 종류마다 따로 선언한다. 노드는 특정 Skill을 가리키고, "모든 Passive Skill" 대상 효과는 두지 않는다(`UpgradeEffect` 주석의 기존 원칙).
- 범용 Effect Engine이 아니다. 연산은 더하기와 비율 둘뿐이다. 무엇을 언제 어디에 하는지는 여전히 종류별 코드가 정한다(CA-003 금지 항목 유지).

### 3.2 실행 수치 = 기본 + Loadout + 버프

```text
실행 수치 = 합성(기본 수치, Loadout 보정, 활성 버프)
                  │          │             └ 전투 중. 버프가 시작하거나 끝날 때만 다시 계산
                  │          └ 전투 조립 때 한 번 (지금과 같다)
                  └ Skill 정의
```

- 지금은 "Skill 실행 수치는 전투 조립 때 확정"이다. 버프가 들어오면 이 전제가 바뀐다. 새 규칙 후보 [미정]: **전투 중에 실행 수치를 바꾸는 것은 버프뿐이다.**
- Skill은 보정이 노드에서 왔는지 버프에서 왔는지 모른다. 둘 다 같은 주소(수치, 연산, 값)로 온다.
- 버프가 시작하거나 끝날 때만 다시 계산한다. 매 틱 계산하지 않는다(BLACKHOLE_PERFORMANCE 3절).

#### 합성 규칙 [미정, 제안 있음]

그래프에서는 파일 안의 노드 순서에 의미가 없으므로 합성이 순서와 무관해야 한다. 지금 코드는 "콘텐츠 노드 순서로 쌓기"로 결정성을 얻었다(CONTENT_DEFINITION 3.5). 도구가 파일을 쓰면 그 순서는 도구의 부산물이 된다.

원작 데모의 강화 설명은 `Breaker Speed Currently: 175%`처럼 현재 합계를 보여 준다. 플레이어는 대신 `+10%`처럼 이번 노드의 몫을 보고 싶어 했다 [원작 S2]. 노드마다 비율을 더하고 그 합계를 보여 주는 방식으로 읽힌다 [분석].

```text
최종 = (기본 + Σ더하기) × (1 + Σ비율)
```

- 비율끼리는 곱하지 않고 더한다. 순서와 무관하고, "현재 175%" 같은 합계 표시와 맞다.
- 공격 주기는 "공격 속도 비율"로 보정하고 `주기 = 기본 주기 ÷ (1 + Σ속도 비율)`로 계산하면 0 이하가 되지 않는다. 지금의 `SkillIntervalMultiply`(× 0.8)는 곱이 쌓인다.

### 3.3 전투 중 버프 — 처치 시 버프, 처치 시 공격 주기 감소

```text
버프 천체 사망 (S05, 즉시 확정)
  ↓ 사망 효과 대기열 (Step 4단계, S06)
버프 효과 처리: 받는 Player의 대상 Skill에 버프를 붙인다
  ↓ 대상 Skill의 실행 수치를 다시 계산 (시작 1회)
  ↓ 지속 시간 끝
다시 계산 (끝 1회)
```

- 사망 효과는 Skill 실행 뒤에 처리된다(GAME_RULES 13절). 그래서 버프는 같은 Step의 Skill 실행에 들어가지 않고 다음 Step부터 적용된다. 이는 새 규칙이 아니라 기존 순서에서 따라 나온다. 덕분에 Skill 사이의 실행 순서가 버프 결과를 바꾸지 않는다.
- 버프는 피해를 만들지 않으므로 효과가 효과를 부르는 연쇄는 없다. 하지만 **되먹임**이 있다: 공격 주기 감소 → 처치 증가 → 버프 다시 획득. 끝나는 조건을 규칙으로 둔다. 예: 중첩 상한, 또는 지속 시간 갱신만 허용, 공격 속도 합계 상한 [미정] (BLACKHOLE_PERFORMANCE 2절).

| 정할 것 [미정] | 선택지 | 근거 |
|---|---|---|
| 대상 | 특정 Skill ID / 모든 Skill | 원작 달은 Breaker만 강화한다 [원작 R7·R9]. 이 레포는 "모든 Passive Skill" 대상을 두지 않으므로 특정 Skill ID를 제안한다. 공격 주기 감소의 대상은 사용자 확인 (Q2) |
| 받는 Player | 지금은 단일 Player | 다인 귀속은 미정. `Damage.Source`는 기록일 뿐 귀속 규칙이 아니다 |
| 다시 얻을 때 | 지속 시간 갱신 / 중첩 / 상한 | 원작 달의 지속 시간은 노드 강화 대상이다 [원작 R9]. 중첩 방식은 미확인 |
| 주기 변경 반영 | 돌고 있는 타이머에 즉시 / 다음 주기부터 | 원작 미확인. 레이저 예고 중 반영 여부도 함께 정한다 |
| 새 Battle | 넘기지 않는다 | GAME_RULES 4·15절에서 따라 나온다 |
| 표현 | 활성 버프 목록(대상, 남은 시간)을 읽기 전용으로 공개 | S09 원칙 |

### 3.4 폭발 — 두 번째 피해형 사망 효과

- 사망 위치 반경 안의 적에게 피해를 준다. 사망 효과를 가진 적은 맞지 않으므로(GAME_RULES 10절) 효과가 효과를 부르지 않는다. 적중 수 ≤ 반경 안의 살아 있는 적 수.
- 원작 초신성의 피해는 강화로 "100%"까지 오른다고 보고됐다. 별 HP에 비례하는 것으로 보이지만 공식은 미확인이다 [원작 R7·R8].
- 자리: `DeathEffectDefinition` 하위 정의, `DeathEffects.Resolve` 분기, Loader 종류 이름. 연쇄 번개와 같은 선례다.
- 표현 기록: 폭발 1회당 위치·반경·맞힌 수. 번개 적중 기록과 따로 두며, 모든 효과의 공통 기록은 만들지 않는다.

### 3.5 사망 효과에 ID를 준다 [제안]

- 원작 개발자는 전기 효과를 연쇄 수·분기 확률·기본 피해로 강화한다고 했고, 높은 등급 천체의 효과 피해에는 추가 배율이 있다고 했다 [원작 R3]. 강화가 효과 종류에 걸리고 여러 천체가 같은 효과를 공유하는 것으로 읽힌다 [분석].
- 지금 효과 정의는 `EnemyData.DeathEffect` 안에 이름 없이 있다. 노드가 "전기 효과의 연쇄 수 +1"을 가리킬 주소가 없다.
- 제안: 사망 효과를 ID가 있는 목록으로 두고 Enemy가 ID로 참조한다. 효과도 Skill처럼 수치 목록을 공개하고, 노드는 효과 ID와 수치로 보정한다.
- 버프 효과도 같은 목록에 든다. 원작의 "달 지속 시간" 노드는 버프 효과의 지속 시간 보정이 된다.

### 3.6 Skill 실행 순서 [제안]

- 지금: 시작 구성 뒤에 해금 Skill이 콘텐츠 노드 순서로 붙는다.
- 제안: 콘텐츠 Skill 목록의 순서로 실행한다. 노드 트리가 Skill 실행 순서에 관여하지 않는다. 3.3에 따라 버프는 같은 Step에 들어가지 않으므로, 피해만 있는 지금은 결과 차이가 거의 없다.

### 3.7 Skill 4종

| Skill | 상태 | 할 일 |
|---|---|---|
| Breaker | 있음 | 수치 목록 공개. 치명타(원작 강화 축)는 [미정] |
| 관통 레이저 | 있음 (CA-003~005) | 수치 목록 공개. 예고 시간을 보정 대상으로 둘지 [미정] |
| 세 번째, 네 번째 | 사용자 확인 (Q1) | CA-001 형식으로 명세한 뒤 CA-003 방식으로 최소 절단. 명세 전에는 자리(빈 클래스)를 만들지 않는다 |

## 4. 노드 그래프

### 4.1 원작에서 확인한 것

| 관찰 | 근거 |
|---|---|
| 본편 노드는 한 단계다. 사면 끝이고 여러 레벨이 없다 | 플레이어 보고 [S2]. 지금 구현과 같다 |
| 노드를 사야 그 너머가 드러난다. 한때 살 수 있는 노드가 적다 | 플레이어 보고 [S2] |
| 트리 화면은 휠로 확대, 끌어서 이동 | 플레이어 보고 [S2] |
| 시작 노드 주변에 5회씩 사는 노드, 에필로그 노드는 1/10부터 10단계 | 플레이어 보고 [S1], 개발자 답변 [S5] |
| 자물쇠 노드는 데모 모드에서 잠긴 노드다. 개발자는 이를 없앨 수 있다고 했다 | 개발자 답변 [S4] |
| 밸런스 업데이트로 노드를 추가·삭제했고, 기존 진행을 모두 돌려주지 못했다 | 개발자 답변 [R10] |
| 가격이 뒤로 갈수록 커지고 T(조) 단위까지 표시된다 | 플레이어 보고 [R5], 개발자 답변 [S3] |
| 노드 수를 크게 늘리기 위한 업데이트 | 개발자 공지 [S6] |
| 트리가 거의 일직선이라는 평 | 플레이어 보고 [R5, S7] |

사용자가 준 스크린샷에서 읽은 것 [분석]:

- 중앙의 육각 노드가 시작점이고, 색마다 가지(초록·파랑·보라·빨강)가 뻗는다.
- 노드는 격자 칸에 놓이고 선은 수평·수직이다. 2×2, 3×3, 4×4, 십자 모양 묶음이 많다.
- 묶음 안에서는 이웃 칸끼리 모두 이어져 순환이 생긴다. 노드마다 선행이 하나인 트리로는 이 연결을 그릴 수 없다.
- 회색 사각 노드에 자물쇠가 있다. 스크린샷이 데모 모드라면 이는 게임 규칙의 잠금이 아니다(Q3).

### 4.2 그래프 모델 [제안]

```text
노드       = ID, 가격, Grant 목록
연결선     = 두 노드 ID (방향 없음)
시작 노드  = 산 이웃이 없어도 드러나는 노드 (지금의 "Requires 없음")

드러남     = 시작 노드이거나, 산 노드와 선으로 이어져 있다
살 수 있음 = 드러남 + 전투 중 아님 + 미보유 + Gold 충분
```

- **선이 보이는 모양이자 구매 조건이다.** 둘을 따로 두면 저작자가 그래프 두 개를 맞춰야 한다.
- 선행은 "이웃 중 하나"(OR)다. 원작의 "사야 너머가 드러난다"와 격자 묶음의 순환 연결에서 읽었다 [분석, Q3].
- 순환을 허용한다. 대신 "모든 노드가 시작 노드에서 닿는다"를 검사한다. 선행 오타가 만들던 거짓 순환 진단(AP3)이 없어진다.
- 지금의 단일 `Requires`는 선이 트리 모양인 경우와 같다. 샘플 노드는 의미를 바꾸지 않고 옮겨진다.
- AND 선행(두 노드를 모두 사야 열림)과 구역 잠금은 원작 근거가 없어 만들지 않는다(CA-004 원칙).
- 노드 상태 네 가지(숨김·드러남·살 수 있음·산 것)는 규칙이 정한다. 숨김 노드를 실루엣으로 보여 줄지는 화면이 정한다. 원작 플레이어는 다음 노드가 미리 보이기를 원했다 [원작 S2].

해금 규칙을 그래프로 옮기면:

- 지금: 해금 전 Skill을 바꾸는 노드는 선행 사슬을 따라가면 그 Skill의 해금 노드에 닿아야 한다(CONTENT_DEFINITION 3.3).
- 그래프: 시작 노드에서 그 노드로 가는 **모든 경로**가 해금 노드를 지나야 한다. 해금 노드를 뺀 그래프에서 시작 노드로부터 그 노드에 닿으면 콘텐츠 오류다.
- 같은 검사가 사망 효과와 천체 해금에도 쓰인다.

### 4.3 노드가 주는 것 — Grant

| Grant 종류 | 주소 | 적용 시점 | 받는 시스템 | 원작 근거 | 지금 |
|---|---|---|---|---|---|
| Skill 해금 | Skill ID | 전투 조립 | Skill | 레이저 해금 (사용자 플레이) | `SkillUnlock` |
| Skill 수치 보정 | Skill ID + 수치 + 연산 + 값 | 전투 조립 | Skill | Breaker 속도·피해·반경 | Skill 종류별 효과 6개 |
| 사망 효과 수치 보정 | 효과 ID + 수치 + 연산 + 값 | 전투 조립 [미정] | S06 | 전기 연쇄 수·피해 [R3], 달 지속 시간 [R9] | 없음 |
| 천체 수치·보상 보정 | Enemy ID + 수치 + 연산 + 값 | 출현 | S03·S05 | — (샘플) | `EnemyHealthMultiply`, `GoldMultiply`, `HqExpMultiply` |
| 성장 공급 보정 | Enemy ID + 수 | 공급 요청 | S08 | 성장 시 소행성 수 강화 | `GrowthSupplyAdd` |
| 천체 종류 해금 | Enemy ID | 공급 요청 | S08 | 별·초신성 해금 [R10] | 없음. 공급표에 반영하는 방식 [미정] |

- Grant 종류는 원작에서 본 노드 종류만큼만 둔다. 종류가 늘어나는 곳은 Grant가 아니라 각 시스템의 수치 목록이다.
- 노드 트리는 Grant를 해석하지 않는다. 받는 시스템이 자기 몫을 꺼내 적용한다. Loader는 받는 시스템이 공개한 목록으로 주소를 검증한다.
- 데이터 모양 예:

```text
{ 종류: SkillStat,   대상: "sample-aura",     수치: "Damage", 연산: Add, 값: 2 }
{ 종류: SkillUnlock, 대상: "sample-laser" }
{ 종류: EffectStat,  대상: "effect-electric", 수치: "Chains", 연산: Add, 값: 1 }
{ 종류: SupplyAdd,   대상: "sample-light",    값: 2 }
```

범위 밖: "행성이 파괴될 때 새 행성이 생길 확률" 노드 [원작 R4]는 공급 계기를 늘린다. GAME_RULES 12절을 바꾸는 F05 작업이다.

### 4.4 Loadout — 유일한 접점

```text
산 노드 ID 목록 (PlayerState)
  │ 노드 트리: 콘텐츠에서 노드를 찾아 Grant를 모은다 (순서 무관)
  ▼
Loadout (Player 한 명, 전투 하나)
  ├ Skill 목록: 시작 구성 + 해금 Skill (Skill 목록 순서)
  ├ Skill ID → 보정 목록
  ├ 효과 ID  → 보정 목록
  └ Enemy ID → 수치·보상·공급 보정
  │ 전투 조립: 각 시스템에 자기 몫만 넘긴다
  ▼
Skill 생성: 정의 + "이 Skill 대상 보정"만 받는다
```

- 지금의 `UpgradeModifiers` 자리다. 다른 점은 효과 종류 분기 대신 주소별로 모으는 것, 수치 적용은 받는 시스템이 하는 것이다.
- 트리 화면의 "현재 175%"와 도구의 미리보기가 같은 코드로 계산된다.

### 4.5 데이터 자리

| 파일 | 소유 | 내용 | 편집 |
|---|---|---|---|
| Skill 목록 | Skill | 종류, 기본 수치 | Inspector 수준 (CONTENT_AUTHORING_PLAN 단계 B) |
| 천체·사망 효과 목록 | S03·S06 | 천체 수치, 효과 ID와 수치 | Inspector 수준 |
| 트리 — 규칙 칸 | 노드 트리 | 노드 ID, 가격, Grant, 연결선, 시작 노드 | 노드 도구 |
| 트리 — 표시 칸 | 트리 화면 | 좌표(격자 칸), 구역·색, 아이콘, 이름, 설명 | 노드 도구 |

- 선은 규칙 칸에, 좌표는 표시 칸에 있다. Core는 규칙 칸만 읽는다.
- 표시 칸은 노드 ID로 규칙 칸에 붙는다. 도구가 두 칸의 ID가 맞는지 검사한다. 표현 사전의 키 누락이 조용히 넘어가던 문제(AP10)를 되풀이하지 않는다.
- 파일 형식(JSON / ScriptableObject)은 팀이 정한다(S11). 도구는 형식이 있어야 시작할 수 있으므로 ST-002에서 정한다.
- 노드 ID는 저장 키다. 도구가 만들고, 표시 이름을 바꿔도 ID는 그대로다. 지금 코드는 산 노드가 콘텐츠에 없으면 전투 조립이 실패한다(`UpgradeModifiers.For`). 원작도 노드를 삭제하며 기존 진행을 돌려주지 못했다 [원작 R10]. 삭제된 노드의 진행 처리는 F04(저장)와 함께 정한다 [미정].

## 5. 노드 저작 도구 (F03)

### 5.1 지금 만드는 이유

CONTENT_AUTHORING_PLAN 8절은 Graph UI를 "노드 수와 연결 수정이 실제 병목이 될 때" 만든다. CA-006 집계는 아직 없다. 이번에는 사용자 요청으로 시작하며, 근거는 규모다.

- 원작 정식판은 업그레이드가 200개 이상이고 [원작 R2], 개발자는 노드를 크게 늘리려고 업데이트를 했다 [원작 S6].
- 지금 형식에는 좌표 칸이 없다(AUTHORING_PAIN 3.5). 스크린샷 같은 배치는 C#으로 쓸 수 없다.
- 이미 기록된 불편: 선행 문자열 반복(AP6), C# 수정만 가능(AP1), 종류에 맞는 칸만 채우기(AP8), 값 없는 효과에 0 쓰기(AP9).

8절의 "예상해서 넣지 않는다"는 그대로 지킨다. 1차는 아래 최소 기능이다. 이후 기능은 도구로 대표 트리를 저작하며 나온 불편으로 고른다(ST-010).

### 5.2 책임

| 한다 | 하지 않는다 |
|---|---|
| 격자 배치, 선 편집, 노드 속성 편집 | 구매 규칙 계산 (Core 규칙을 호출한다) |
| 즉시 검증 (Loader와 같은 코드) | Skill 실행, 전투 |
| 구매 미리보기, Loadout 합계 보기 | 게임의 트리 화면 (F02) |
| 파일 저장·불러오기 | 파일 형식 결정 (ST-002) |

### 5.3 1차 기능

1. **격자 캔버스**: 휠 확대, 끌어서 이동(원작 트리 화면과 같은 조작). 칸에 노드를 놓고 옮기고 지운다. 한 칸에 노드 하나.
2. **선**: 두 노드를 잇고 끊는다. 방향이 없다.
3. **속성 패널**: ID(자동, 표시만), 가격, Grant 목록, 이름·설명·아이콘·구역.
   - Grant는 종류 → 대상 ID 목록 → 대상의 수치 목록 → 연산 → 값 순서로 고른다. 문자열을 치지 않는다(AP6).
   - 값이 없는 종류(해금)는 값 칸이 없다(AP9).
4. **검증 목록**: 누르면 그 노드로 이동한다.
   - 시작 노드에서 닿지 않는 노드
   - 없는 대상 ID, 대상에 없는 수치·연산
   - 해금 노드를 거치지 않고 닿는 강화 노드
   - 한 Skill의 해금 노드가 둘 이상, 시작 구성 Skill의 해금
   - 규칙 칸과 표시 칸의 ID 불일치, 한 칸에 겹친 노드
5. **미리보기**: 노드를 눌러 "산 것"으로 두면 드러남·살 수 있음 상태와 Loadout 합계(예: Breaker 피해 3 → 7, 공격 속도 175%)가 보인다.
6. **저장·불러오기**.

1차에 넣지 않는 것 (불편이 확인되면 고른다): 묶음 템플릿(3×3 자동 생성·연결), 복사·붙여넣기, 가격 곡선 일괄 적용, 미리보기 상태로 전투 시작(P10·S12), 검색.

### 5.4 기술 [제안]

- Unity Editor 창, Editor 어셈블리. Core는 Unity 없이 컴파일되는 지금 상태를 유지한다(CoreSmoke).
- GraphView(`UnityEditor.Experimental.GraphView`)는 포트와 방향 있는 선을 전제로 한다. 격자 칸과 무방향 선에는 맞지 않아 캔버스를 직접 그리는 쪽이 단순할 것으로 본다. 시작 전에 짧은 시험으로 확인한다.
- 게임의 트리 화면(F02)과는 표시 칸 형식만 공유하고 코드는 공유하지 않는다.

## 6. 사용자의 UI·사운드·아트 작업과 맞닿는 곳

| 먼저 세팅해도 되는 것 | 계약이 정해진 뒤 연결할 것 | 계약이 나오는 티켓 |
|---|---|---|
| 트리 화면의 틀: 확대·이동, 노드·선 그리기, 네 가지 상태의 모양 | 노드 목록·좌표·선·표시 칸 읽기 | ST-008 |
| 구매 버튼과 결과 피드백 (구매됨 / 잠김 / Gold 부족 / 이미 보유) | NodeId 요청 → `PurchaseResult` | 지금 있음 |
| 노드 아이콘·색 에셋 | 노드 상태 조회 (숨김 / 드러남 / 살 수 있음 / 산 것) | ST-004 |
| 노드 설명 문장의 틀 | "현재 합계" 값 (Loadout 조회) | ST-003 |
| 폭발·버프 VFX·SFX | 폭발 기록, 활성 버프 목록 | ST-006, ST-007 |

- 노드 설명 문장은 지금 `Hud.Describe`가 효과 종류 분기로 만든다. 제안: 문장은 도구의 표시 칸에 쓰고, 수치 값만 끼워 넣는다. 화면이 Skill 수치 이름을 알 필요가 없어진다.

CONTENT_AUTHORING_PLAN과 같은 순서를 쓴다: 명세 → 경계 절단 → 콘텐츠 → 도구 → 저작 시험.
