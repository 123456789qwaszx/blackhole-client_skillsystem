## 1. 이 문서의 역할

이 문서는 **무엇을 하나의 개발 책임으로 묶고, 다른 담당자에게 무엇을 제공할지** 정한다. 기존 PLAN의 마일스톤은 완료된 Reference 제작 기록이다. 아래 목록은 마일스톤을 다시 수행하라는 계획이 아니다.

기존 코드를 인수·활용하면서 최신 규칙과의 차이를 확인하고, 팀 게임에 필요한 작업을 티켓으로 나누는 출발점이다. 하나의 시스템이 반드시 클래스 하나, 폴더 하나, 담당자 한 명이어야 하는 것은 아니다.

## 2. 시스템 총괄표

- **MVP**: 현재 플레이 성립에 필요한 시스템.
- **지원**: 제작·검증을 위한 개발 작업.
- **후속**: 존재를 목록화하되, 별도 규칙 확정 전에는 MVP 작업에 포함하지 않는다.
- **구현 있음**: 기준 커밋에 대응 코드가 있다는 뜻이다. 최신 규칙의 인수 완료나 제품 완성을 의미하지 않는다.

## 3. MVP 시스템 명세

아래 인수 기준은 담당자가 작업을 마친 뒤 다른 개발자가 확인할 수 있는 결과다. 기존에 충족하는 항목은 재구현하지 않고 검증 근거를 연결한다.

### S01. Battle 수명·시간

- **소유**: 실행/종료 상태, 전투 시간, 현재 전투 인스턴스의 수명.
- **입력 → 출력**: 시작·다시 시작 요청 / 경과 시간 / 시간 연장 → Step 실행 / 종료 결과 / 새 전투.
- **책임 경계**: 각 전투 규칙의 내용을 직접 구현하지 않고, 처리 순서와 종료 경계를 보장한다. 업그레이드 구매·저장 정책은 여기서 결정하지 않는다.
- **접점**: S07의 시간 연장, S08의 시작 공급, S09·S10의 정리와 화면 전환, S11의 실행 구성.
- **인수 기준**:
  - 같은 Step의 사망 효과와 성장·시간 연장·공급을 처리한 뒤 종료한다.
  - 종료 후 공격·사망·성장 결과를 추가로 만들지 않는다.
  - Cleanup은 처치가 아니므로 EXP와 사망 효과를 만들지 않는다.
  - 다시 시작하면 Enemy·HP·위치·Skill Timer·사망/흡수 표현이 새 전투로 섞이지 않는다.
- **구현 참고**: `Core/Session/`, `Unity/SessionLauncher.cs`.

### S02. HQ 기준 공간·입력

- **소유**: 화면과 Gameplay 좌표의 변환, Player의 현재 Aim Point.
- **입력 → 출력**: 마우스 화면 위치 → HQ 원점 기준 Aim Point.
- **책임 경계**: 공격 위치만 전달한다. 공격 시점과 Damage를 결정하지 않는다.
- **접점**: S03·S08·S09는 같은 공간을 사용하고, S04는 Aim Point를 읽는다.
- **인수 기준**:
  - Gameplay의 HQ는 항상 `(0,0)`이다.
  - 초기 배치·공전·흡수 도착점이 같은 원점을 사용한다.
  - 화면의 공격 범위 중심과 실제 공격 중심이 일치한다.
  - 카메라/화면 변환을 수정해도 입력과 표시가 어긋나지 않는다.
- **주의**: HQ가 원점이라는 뜻은 공격 중심도 HQ라는 뜻이 아니다. 기본 공격의 중심은 Aim Point다.
- **구현 참고**: `Unity/SceneSpace.cs`, `Unity/HostInput.cs`, `Core/Players/Player.cs`, `Core/Hq/Hq.cs`.

### S03. Enemy 상태·행동

- **소유**: 개체별 HP, Position, Alive/Dead, 실행 수치.
- **입력 → 출력**: 생성 데이터 / Step 시간 / 피해 → 새 위치 / HP 변화 / 최초 사망 여부.
- **책임 경계**: 공전과 피해 수용을 담당한다. EXP 지급, 번개 실행, 사망 연출은 담당하지 않는다.
- **접점**: S08 생성, S04·S06 피해 요청, S05 사망 처리, S09 상태 표시.
- **인수 기준**: 각 개체 상태가 독립적이며 HQ 원점 둘레를 공전한다. 죽은 적은 이동·피해·재사망하지 않는다. Player 추적이나 행동 전환은 MVP에 추가하지 않는다.
- **구현 참고**: `Core/Enemies/`.

### S04. Passive Attack

- **소유**: Skill Timer, 실행 반경·피해량·주기, 공격 Tick 상태.
- **입력 → 출력**: Aim Point / 시간 / 살아 있는 Enemy → 범위 내 모든 대상에 피해 요청.
- **책임 경계**: 처치 보상과 사망 결과는 S05에 맡긴다. 화면이 자체 타이머로 공격을 실행하지 않는다.
- **접점**: S02 입력, S03 대상, S05 피해, S09 범위 표시.
- **인수 기준**:
  - 첫 Tick은 Battle 시작 시점이고 이후 일정 주기로 실행한다.
  - 빈 Tick도 소비하며 다음 공격으로 이월하지 않는다.
  - 범위 안은 전부, 밖은 제외한다.
  - 범위 표시와 판정에 같은 반경을 사용한다.
- **남은 결정**: Enemy 중심 포함인지 외곽 겹침인지, 조준점이 없는 시작 프레임의 처리. 현재 샘플은 중심 판정이며 조준점이 없으면 빈 Tick이다.
- **구현 참고**: `Core/Skills/`.

### S05. Damage·Death Result

- **소유**: 사망 결과 확정 절차와 사망 기록. Enemy HP는 S03, HQ EXP는 S07이 소유한다.
- **입력 → 출력**: 피해와 대상 → 사망 확정 / Gameplay 대상 제외 / HQ EXP / 사망 기록 / 효과 실행 요청.
- **책임 경계**: 일반 공격과 Death Effect가 같은 절차를 사용한다. 흡수 연출의 완료를 기다리지 않는다.
- **접점**: S03·S04·S06·S07·S09.
- **인수 기준**:
  - 같은 적에 피해가 겹쳐도 EXP와 사망 기록은 한 번만 발생한다.
  - HP가 0 이하가 된 순간 Gameplay에서 제외한다.
  - 사망 연출을 끄거나 늦춰도 EXP와 성장 결과는 같다.
  - Cleanup은 이 절차의 처치 결과를 만들지 않는다.
- **구현 참고**: `Core/World/World.cs`, `Core/Combat/Damage.cs`, `DeathRecord.cs`, `Core/Enemies/EnemyReward.cs`.
- **범위 주의**: 기존 Gold 지급은 후속 경제의 구현 참고이며 MVP의 필수 보상은 HQ EXP다.

### S06. Death Effect

- **소유**: 실행 대기 효과, 현재 번개의 적중 대상과 횟수, 표현용 적중 기록.
- **입력 → 출력**: 특수 Enemy 사망 / 효과 정의 / 사망 위치 → 피해 요청 / 번개 적중 기록.
- **책임 경계**: 피해·사망 결과는 S05를 재사용한다. 번개 선이나 애니메이션은 S09가 담당한다.
- **인수 기준**:
  - Death Effect를 가진 Enemy는 효과 피해 대상에서 제외한다. 다른 종류의 Death Effect도 포함한다.
  - 유한한 최대 적중 수와 대상 부재 등 명시된 종료 조건이 있다.
  - 효과 처치 역시 EXP를 한 번만 지급하고 같은 Step의 성장에 반영된다.
- **남은 결정**: 범위, 최대 횟수, 대상 선택 순서. 현재 구현의 최근접·동일 대상 재적중 금지·동거리 목록 순서는 샘플 선택이며 원작의 확정 규칙이 아니다.
- **구현 참고**: `Core/Combat/DeathEffects.cs`, `DeathEffectDefinition.cs`, `DeathEffectHit.cs`.

### S07. HQ 성장·Growth Milestone

- **소유**: HQ EXP·Level, 이미 처리한 성장 구간.
- **입력 → 출력**: 사망 EXP / 성장 정의 → Level 변화 / Milestone 시간 연장 / 공급 요청.
- **책임 경계**: HQ Level을 Player 공격력에 자동 연결하지 않는다. 실제 적 생성은 S08, 성장 연출은 S09가 담당한다.
- **인수 기준**:
  - 한 번에 여러 Threshold를 넘어도 필요한 Level 상승을 모두 처리한다.
  - **일반 Level과 Milestone을 구분**한다. 일반 Level에는 시간·공급 효과가 없다.
  - 건너뛴 Milestone도 각각 한 번만 처리한다.
  - 시간 연장은 해당 Step의 종료 판정보다 먼저 반영한다.
- **남은 결정**: Threshold 표, Milestone Level, 연장 시간, 공급 수량. 값은 S11에서 관리한다.
- **구현 참고**: `Core/Hq/`, `Core/Progression/GrowthProgression.cs`.

### S08. Enemy 공급·배치

- **소유**: 공급 요청과 처리 상태, 생성 순번. 생성된 개체 상태는 S03이 소유한다.
- **입력 → 출력**: Battle Start 또는 Milestone의 종류·수량 요청 → HQ 주변 Enemy 생성.
- **책임 경계**: 공급은 무엇을 몇 개 만들지, 배치는 어디에 어떻게 만들지다. 하나의 담당 묶음으로 인수하되 두 책임을 구별한다.
- **인수 기준**:
  - 시작 공급은 Battle당 한 번, Milestone 공급은 도달한 구간당 한 번 발생한다.
  - 시간 경과만으로 공급하지 않는다. 요청 수량은 유한하다.
  - 새 적은 공급 이전의 공격 대상으로 소급하여 들어가지 않는다.
  - 이전 Battle의 요청이 다음 Battle에 남지 않는다.
- **남은 결정**: 위치 분포, 겹침, 허용 최대 개체 수, 상한 도달 시 처리. 사건 기반 공급만으로 전체 개체 수 상한이 증명되지는 않는다.
- **구현 참고**: `Core/Supply/`, `Core/Spawn/`.

### S09. 전투 표현

- **소유**: 화면 객체, 파괴·흡수·번개 등의 표현 수명과 기록 소비 상태.
- **입력 → 출력**: 읽기 전용 전투 상태 / 사망·적중 기록 → 화면과 연출.
- **책임 경계**: 연출은 HP·EXP·시간·공급을 변경하지 않는다. 흡수 도착점은 HQ 원점이다.
- **인수 기준**:
  - 사망 즉시 Gameplay에서 빠진 적의 표현만 별도로 지속할 수 있다.
  - 여러 Step의 기록을 한 프레임에 받아도 사망·적중 연출이 누락되거나 중복되지 않는다.
  - 공격 범위 표시는 S04의 실제 값을 사용한다.
  - 새 Battle에서 이전 사망·흡수·번개가 남지 않는다.
  - 피격, 사망, 성장, 시간 연장을 플레이어가 구별할 수 있다.
- **남은 결정**: 아트·사운드 범위, 동시 표현 한도, 연출 생략 방식. 연출 길이 0과 명시적 비활성화의 동작도 구분해 확인한다.
- **구현 참고**: `Unity/WorldView.cs`, `Unity/Sample/SamplePresentation.cs`.

### S10. HUD·전투 화면 흐름

- **소유**: HUD와 종료·재시작 화면 상태, 사용자 요청 전달.
- **입력 → 출력**: 시간·EXP·Level·종료 상태 → 화면 표시 / 시작·재시작 요청.
- **책임 경계**: 시간을 직접 줄이거나 종료 결과를 계산하지 않는다. 구매 화면은 F02의 후속 책임이다.
- **인수 기준**: 실제 상태와 표시가 일치한다. 종료 후 재시작할 수 있고, 화면 전환 중 입력이 끝난 전투에 새 결과를 만들지 않는다.
- **구현 참고**: `Unity/Hud.cs`, `Unity/SessionLauncher.cs`, `Unity/GameHost.cs`.

### S11. 콘텐츠 정의·검증

- **소유**: Enemy·Skill·성장·시작 공급·배치·전투 시간 데이터와 검증.
- **입력 → 출력**: 저작 데이터 → 유효한 정의 / 원인을 찾을 수 있는 오류.
- **책임 경계**: 기획 수치의 원본을 한 곳에 둔다. 파일 형식이나 ScriptableObject 채택은 팀이 정하며, 전용 편집기는 별도 범위다.
- **인수 기준**: 누락된 참조·잘못된 수치로 전투를 부분 조립하지 않는다. 오류 위치를 찾을 수 있다. 실행 상태 변경이 원본 정의를 변경하지 않는다.
- **남은 결정**: 최소 샘플 콘텐츠, 데이터 담당·형식, 일반 Level과 Milestone 구분 표현, 허용 상한.
- **구현 참고**: `Core/Content/`, `Sample/SampleContent.cs`.

### S12. 디버깅·성능 검증

- **소유**: 기준 시나리오, 재현 명령, 측정 결과. 각 시스템의 최적화는 해당 담당자와 함께 수행한다.
- **입력 → 출력**: 고정된 콘텐츠·입력·기기 조건 → 재현 가능한 전투 / 측정값 / 변경 전후 비교.
- **인수 기준**:
  - 최소 지원 기기, 목표 FPS, 허용 개체·동시 사망·효과 규모를 명시한다.
  - 지정 Level·공급·다수 사망 등 기준 상황에 빠르게 진입할 수 있다.
  - Core 계산과 Unity 표현을 포함한 실제 빌드 비용을 구분하여 기록한다.
  - 병목을 측정하고 한 변경의 효과를 같은 조건에서 비교한다.
- **주의**: 성능 원칙의 60 FPS·개체 수 예시는 확정 합격선이 아니다. CoreBench 수치를 전체 게임 FPS로 환산하지 않는다. ECS·풀링 등 기술을 선결 조건으로 지정하지 않는다.
- **구현 참고**: `tests/CoreSmoke/`, `tests/CoreBench/`, `Assets/BlackHole/Tests/EditMode/Contracts/`.

## 4. 시스템 사이의 연결 계약

이 표는 데이터 흐름이다. 모두 별도 이벤트 버스나 새 인터페이스로 구현하라는 뜻이 아니다.

| 생산자 → 소비자 | 전달할 것 | 반드시 합의할 조건 |
|---|---|---|
| S02 → S04·S09 | Aim Point | HQ 기준 좌표, 입력 부재 처리 |
| S04·S06 → S05 | 대상과 피해 | 죽은 대상 무시, 사망 결과 중복 금지 |
| S05 → S07 | HQ EXP | 사망 순간 확정, Cleanup 제외 |
| S05 → S06·S09 | 사망 위치·종류·효과 정보 | Gameplay 객체를 연출 종료까지 유지하지 않음 |
| S06 → S09 | 번개 적중 기록 | 피해는 이미 확정, 표현은 읽기만 함 |
| S07 → S01·S08 | 시간 연장·공급 요청 | Milestone당 한 번, 종료 판정보다 먼저 |
| S08 → S03 | 생성된 실행 상태 | HQ 원점 기준, 공급 전 공격에 소급 참여하지 않음 |
| S01 → S09·S10 | 종료와 전투 교체 | 잔여 표현 정리, 새 전투 상태 사용 |
| S11 → 각 실행 시스템 | 검증된 정의 | 샘플 수치와 확정 규칙 구분 |

한 Gameplay Step의 순서는 GAME_RULES_MVP 13절을 따른다.

1. Enemy Action
2. Passive Attack
3. Damage / Death
4. Death Effect
5. HQ EXP / Level 반영
6. Growth Milestone
7. Enemy Supply
8. Battle End 판정

S05의 사망 결과는 즉시 확정한다. 위 순서는 사망 결과를 연출 이후로 미루라는 뜻이 아니며, **Death Effect까지 포함한 결과가 Milestone 판정에 들어간다**는 기준이다.

## 5. 기존 구현을 인수할 때 확인할 차이

이번 문서는 코드 변경을 수행하지 않는다. 아래는 기준 커밋을 읽어 확인한 차이와 점검 항목이다.

| 항목 | 현재 구현 | 최신 기준에 맞춘 인수 작업 | 담당 후보 |
|---|---|---|---|
| HQ 좌표 | HqDefinition은 임의 Position을 허용하고 샘플만 0,0 사용 | 원점 규칙이 데이터·입력·표현에서 유지되는지 확정 | S02·S11 |
| 일반 Level / Milestone | HqLevelDefinition은 효과 없는 Level을 표현할 수 있으나 SampleContent는 Lv2~10 모두 시간·공급 부여 | 일반 Level과 Milestone이 함께 있는 샘플로 구분 검증 | S07·S11 |
| EXP 반영 시점 | World.DealDamage가 사망 즉시 EXP·Level 반영, 효과 대기열 처리 후 성장 효과 실행 | 규칙의 결과 확정과 Step 순서 설명을 일치시키고 효과 처치 포함 확인 | S05·S07 |
| 종료 후 흐름 | SessionLauncher가 구매 화면을 열고 Gold·구매를 다음 전투에 유지 | MVP 인수는 종료→새 Battle을 기준으로 하고 경제는 별도 판정 | S01·S10 |
| 공급 상한 | 사건별 수량과 유한 성장표가 있음 | 팀 콘텐츠의 최악 동시 개체 수와 상한 처리 정책 산정 | S08·S11·S12 |
| 공격 판정 | Enemy 중심 거리 사용 | 외곽 겹침 여부를 임시 선택으로 표시하고 합의 | S04 |
| 표현 품질·성능 | 원판·선·IMGUI 중심 샘플과 Core 벤치마크 | 제품 표현 범위와 실제 빌드 기준 시나리오 검증 | S09·S10·S12 |

과거 계약의 통과 수는 새 규칙 충족의 대체물이 아니다. 특히 임의 HQ 위치를 허용하는 과거 계약과 새 원점 규칙은 같은 기준으로 취급하지 않는다.

## 6. 후속 시스템을 나누는 기준

업그레이드를 하나의 거대한 작업으로 배정하지 않는다.

| ID | 독립 책임 | 다른 시스템과의 접점 | 착수 전에 정할 것 |
|---|---|---|---|
| F01 | 구매 판정과 효과 적용 | F04의 재화·구매 기록, 각 수치 적용 대상 | 가격, 선행 AND/OR, 중복 구매, 효과 합성·적용 시점 |
| F02 | 플레이어가 보는 노드 트리 | F01 구매 요청/결과, F03 배치 데이터 | 잠김·구매 가능·구매 완료 표시, 이동·확대, 구역 노출 |
| F03 | 개발자가 쓰는 노드 편집 | S11 검증·데이터 출력, F02 배치 형식 | 전용 도구의 필요성, 노드 ID·연결·좌표 형식 |
| F04 | 경제와 전투 밖 상태·저장 | F01·S01 | 무엇이 유지되는지, 저장 시점·버전, 실패 처리 |
| F05 | 새 콘텐츠 종류 | S03·S04·S06·S08·S11 | 기존 수치 변형인지 새 동작인지, 연쇄·공급 상한 |
| F06 | 새 플레이/통신 규칙 | Player·World·Session 전반 | 참가자·보상 귀속·상태 권위·동기화·실패 조건 |

F03은 플레이어 화면이 아니다. F02의 노드 좌표 편집과 F01의 구매 규칙도 별개다. 기존 샘플이 있다는 이유로 후속 정책을 이미 합의한 것으로 간주하지 않는다.

## 7. 6인 팀의 분담 후보

인원 수에 맞춘 강제 배정표가 아니라 **서로 맞물리는 책임을 묶은 초안**이다. 실제 이름과 일정은 팀원 숙련도·가용 시간 확인 후 채운다.

| 작업 묶음 | 포함 시스템 | 인수할 결과 | 주 협업 대상 |
|---|---|---|---|
| A. 전투 흐름·통합 | S01, S02 | 시작→입력→종료→재시작, 공통 Step 순서 | B·C·D·E |
| B. Enemy·전투 판정 | S03, S04, S05 | 공전→자동 공격→사망·EXP | A·C·D |
| C. 성장·공급·특수 효과 | S06, S07, S08 | 번개→성장 구간→연장·공급 | A·B·D·F |
| D. 전투 화면·연출 | S09 | 피격·사망·흡수·번개·성장 표현 | B·C·E |
| E. HUD·플레이 흐름 UI | S10 | 시간·성장 표시, 종료·재시작 UI | A·D |
| F. 콘텐츠·검증 도구 | S11, S12 | 검증된 데이터, 재현 환경과 측정 결과 | 전원 |

- B·C는 규칙 접점이 많고 D는 표현 품질에 따라 작업량이 크게 달라진다. E·F와 세부 티켓을 재배분한다.
- 각자 독립 확인에는 고정 샘플·기록 대역을 사용하고, 최종 완료는 실제 Battle 연결로 확인한다.
- 후속 트리 기능이 승인되면 E는 F02, F는 F03, 관련 규칙 담당은 F01의 적용 부분을 맡는 식으로 확장할 수 있다. 이는 현재 착수 지시가 아니다.

### 공동 수정 파일

| 파일 | 통합 책임 후보 | 변경 시 함께 확인할 담당 |
|---|---|---|
| World.cs | A | B·C: Step 순서와 사망 경계 |
| SessionAssembler.cs | A | B·C·F: 조립과 실행 상태 수명 |
| ContentData.cs / ContentLoader.cs | F | 정의를 추가하는 담당 |
| SampleContent.cs | F | 해당 규칙 담당 |
| WorldView.cs | D | B·C: 상태·기록 전달 |
| Hud.cs / SessionLauncher.cs | E / A | 종료·전환 접점 변경 시 A·E |

통합 책임자는 모든 코드를 대신 작성하는 사람이 아니다. 접점 변경의 영향과 병합 결과를 확인한다.

## 8. 티켓으로 옮기는 형식

시스템 이름만으로 “담당/완료”를 표시하지 않는다. 각 시스템 아래 실제 남은 결과를 티켓으로 분리한다.

| 필드 | 기록 내용 |
|---|---|
| 티켓 ID / 시스템 ID | 예: T-001 / S07 |
| 목표 | 플레이 또는 개발 흐름에서 달라질 결과 |
| 작업 종류 | 기존 구현 인수 / 규칙 정합성 수정 / 제품 구현 / 후속 설계 |
| 범위 | 이번 작업에 포함되는 구체적인 변경 |
| 입출력·연결 담당 | 전달 데이터와 상대 담당자 |
| 완료 조건 | 재현 가능한 동작과 증거 |
| 선행 조건 | 필요한 데이터·정책·다른 티켓 |
| 담당 / 검토 | 실제 팀원 이름 |
| 예상 시간 / 실제 시간 | 담당자가 인수 조사 후 시간 단위로 작성 |
| 상태 / 근거 | 대기·진행·검토·완료, 커밋·영상·측정 결과 |

초기 티켓 후보:

| 티켓 | 목표 | 연결 시스템 | 완료 증거 |
|---|---|---|---|
| T-001 | 일반 Level과 Milestone의 구분을 샘플로 검증 | S07·S11 | 일반 Level은 연장·공급 없음, Milestone은 각각 1회 |
| T-002 | HQ 원점과 입력·표시 좌표 정합성 인수 | S02·S09·S11 | 배치·공전·흡수·조준이 동일 공간에서 일치 |
| T-003 | 전투 종료→새 전투의 MVP 흐름 인수 | S01·S10 | 이전 실행 상태·연출 잔여 없는 반복 플레이 |
| T-004 | 종료 직전 번개 처치→성장→연장을 통합 확인 | S01·S05·S06·S07 | 같은 Step의 연장 반영 후 종료 판정 |
| T-005 | 성능 합격선과 기준 상황 확정·재현 | S08·S11·S12 | 기기·콘텐츠·입력·측정 조건이 명시된 결과 |
| T-006 | 샘플 전투 표현을 제품 표현으로 구체화 | S09·S10 | 상태와 표현 일치, 연출 생략 시 게임 결과 동일 |

소요 시간은 현재 Reference 제작 시간이나 코드 줄 수로 확정하지 않는다. **각 담당자가 기존 구현을 확인한 뒤 남은 작업만** 추정한다. 후속 기능의 정책 결정 대기와 구현 시간도 구분한다.
